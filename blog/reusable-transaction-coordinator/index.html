Making Distributed Transactions Easier to Trust

July 11, 2026 · 9 min read
Andres Gutierrez
Creator of Kahuna

Distributed transactions are difficult for a simple reason: a transaction is more than its final commit. It is a conversation made of reads, writes, locks, retries, timeouts, and sometimes failures at the worst possible moment. If each client has to remember every detail of that conversation, correctness depends too much on code outside the database.

We want Kahuna to take more responsibility for this process. The direction is to build a reusable transaction coordinator that owns the transaction state on the server, provides one consistent protocol to clients, and makes failure behavior easier to understand.

One Handle, One Source of Truth​

Today, a client can participate in coordination by tracking modified keys, acquired locks, and read dependencies. This works, but it creates an uncomfortable question: what happens if the client forgets one item when it asks to commit?

The server should not have to trust a list assembled at the last moment. It already sees the operations, so it should build the transaction's working set as those operations succeed.

With the new model, the client will keep an opaque transaction handle. This handle will identify the transaction and route requests back to its coordinator. Reads, writes, lock operations, commit, and rollback will all use it. The details of the working set will remain on the server.

This gives us a clear source of truth. When a key is modified, the coordinator records it. When a lock is acquired or released, the coordinator updates its state. When a read must be checked for a conflict, the coordinator keeps the observation. Commit and rollback will use this server-owned state instead of accepting coordination lists from the caller.

For application developers, the public API should feel smaller. For the system, the rules become stronger because a caller cannot accidentally omit part of the transaction.

Closing the Door Before Finalization​

There is a subtle race in any interactive transaction. Imagine that one request is writing a key while another request starts commit. If commit takes a snapshot of the working set too early, the write may finish without being included. If it takes the snapshot too late, finalization may wait forever for new operations.

We plan to solve this with a clear closing step. The first close, commit, or rollback request will stop the transaction from accepting new operations. It will then wait for operations that were already registered to finish. Only after that will the coordinator freeze an immutable view of the working set.

This frozen view will be reused by every later finalization attempt. It also gives integrations a safe moment to do pre-commit work. For example, a database using Kahuna may need the final list of modified keys before publishing cache changes. A normal status query is useful while the transaction is open, but only the closed snapshot can promise that no late write will appear.

The important idea is simple: finalization starts by closing the door, then waits for everyone who was already inside.

Safe Retries for Every Operation​

Networks make outcomes uncertain. A server may complete a write, but the response can be lost before the client receives it. Retrying with no identity can apply the same logical operation twice. Avoiding the retry is not safe either, because the client cannot know whether the first request ran.

Each transaction operation will therefore have its own stable operation ID. The client will create one ID for one logical request and reuse it when retrying that request. Before changing participant state, the operation will be registered with the coordinator. After it finishes, its confirmed effects will be merged into the working set.

Participants will keep recent results long enough to recognize a retry. If a response was lost, the same operation can return its previous result and complete its registration without applying the change again. Reusing an ID for a different request will be rejected.

There is a deliberate safety choice here. If the coordinator knows that an operation may be running but cannot confirm its result, commit must wait or ask the caller to retry. A temporarily stuck transaction is preferable to a successful commit that silently misses a write.

A Reusable Core, Not a Second Script Engine​

Kahuna already has strong transaction machinery inside its scripting path. It includes read validation, two-phase commit, lock cleanup, and rollback behavior. However, the generic coordination logic and the script executor currently live too close together.

We want to separate these responsibilities. The coordinator will manage transaction identity, lifecycle, working sets, operation registration, finalization, and cleanup. The script executor will continue to manage parsing, variables, expressions, and script-specific execution.

The script engine can then use the coordinator rather than define what a transaction coordinator is. Interactive clients and other systems will use the same core guarantees without carrying script concepts into their own transaction flow.

This separation is also important for reuse beyond the .NET client. The protocol should describe stable behavior that any SDK can follow: keep the transaction handle, keep one operation ID per logical request, and let the server own coordination state.

Finalization Is a State Machine​

Commit and rollback are not simple buttons. Duplicate requests can arrive at the same time, a retry can overlap with an earlier attempt, and an abandoned transaction can be cleaned up while a client is still waiting for a response.

The coordinator will serialize these paths through one finalization state. If an attempt is already active, duplicate requests will wait for and observe the same result. Once the transaction reaches a terminal outcome, that outcome will not change. A committed transaction stays committed, and a rolled-back transaction stays rolled back.

Not every unsuccessful attempt is terminal. A temporary routing problem, an unavailable participant, or an operation that has not finished may mean “retry this same action.” In that case, the finalization slot must become available for a later attempt. A retryable response should not permanently consume a one-shot gate.

The same rule will apply to automatic cleanup. The reaper that handles expired sessions must coordinate with explicit commit and rollback calls, rather than racing them from a separate path.

Concurrency Choices Should Be Explicit​

Different applications need different transaction behavior. Some want pessimistic locking. Others prefer optimistic concurrency and validate their reads at commit. Snapshot-based systems may already have their own read timestamp and should not repeat the same validation in Kahuna.

The transaction will begin with an explicit policy that covers locking, read behavior, timeout, release behavior, and decision durability. Invalid combinations will be rejected early instead of being interpreted in a surprising way.

This is especially helpful when Kahuna is used as a coordination layer for another database. The database can keep its own isolation rules while relying on Kahuna for the shared transaction lifecycle. The boundary between the two systems becomes visible and testable.

Durable Commit Decisions, with Honest Limits​

The most demanding part of the work is recovering after a commit decision has been made but before every participant has acknowledged it.

For persistent data, we plan to offer an opt-in durable decision mode. Before sending the first commit command to a participant, the coordinator will replicate the commit decision. Each participant will record a durable completion receipt together with the committed value. The coordinator will then persist acknowledgement progress and continue retrying unfinished participants after a coordinator restart or leadership change.

The order matters. First, the participant commits the value and its receipt. Next, the coordinator records that acknowledgement durably. Only then may the participant forget the receipt. This prevents a delayed retry from confusing “already committed” with “unknown transaction.”

Durable decisions will cost more coordination and replication, so they will not be the default for every workload. They will also reject transactions that modify ephemeral values. A recoverable commit decision cannot promise that in-memory data will survive a process loss.

We also want to be precise about what this mode does not solve. The active interactive session will still be held in memory before the commit decision. Prepared participant state will not become durable as part of this work. If a participant loses leadership after prepare but before its commit, the new leader may not have enough information to finish. The correct response in that case is to report that the operation must be retried, not to claim a guarantee the system cannot provide.

Good distributed-system design is not only about adding stronger guarantees. It is also about making the remaining boundaries clear.

What This Means for Clients​

The client-side transaction session will become lighter. It will retain the opaque handle, policy, operation IDs, and local status, but it will no longer be the authority for keys, locks, or read dependencies. Client-side synchronization may still improve the developer experience, while server-side coordination will provide the actual correctness.

Other systems built on Kahuna will be able to remove duplicate coordination state. They may still keep their own session registry, isolation mode, cache protocol, schema information, and application timeouts. Those are domain responsibilities. The reusable coordinator should own only the shared mechanics that are easy to get wrong: operation fencing, working-set tracking, finalization, retries, and cleanup.

There is a performance trade-off. Registering and confirming each interactive operation adds coordinator traffic. We will measure point operations, batches, validated reads, and snapshot reads before deciding where batching, locality, or streaming can reduce the cost. The first goal is a correct protocol; the next is making that protocol efficient.

The Direction​

The result we are aiming for is not a magical transaction system where failures disappear. It is a coordinator with understandable ownership and predictable answers.

Clients should be able to say, “this is my transaction,” without also carrying a fragile summary of everything it has done. Duplicate requests should converge on one outcome. A late operation should never slip past commit. Durable mode should recover the decisions it truly knows, and best-effort mode should remain honest about what can be lost.

That foundation will make Kahuna transactions easier to use directly and easier to reuse inside larger systems. More importantly, it will move the hardest correctness rules into one place, where we can test them under concurrency, retries, leadership changes, and process failures.

That is the kind of simplicity we want: not fewer moving parts inside the system, but fewer ways for its users to make a distributed transaction unsafe.
