Inside Kahuna's
Distributed Transactions

How several key/value changes share one outcome, even across partitions

Andres Gutierrez kahunakv/kahuna Kahuna 1.14.3 · source 7c84fc1c from a balance transfer to failure recovery

A balance transfer needs two changes: subtract from one account and add to another. If the accounts live on different servers, a failure must not leave only half the persistent transfer committed. Kahuna coordinates those changes through one authoritative commit or abort decision.

This paper explains that protocol, starting with an example. The key distinction is staged → prepared → committed: accepting a write into an open transaction does not commit it. Replicated preparation preserves the proposed value; the final decision determines its outcome.

New to distributed systems? Start with the transfer and the vocabulary, then use the interactive diagram below to follow the protocol. For application APIs, see Transactions.

I. Start With a Transfer

Suppose Alice has 100 units and Bob has 50. Run the setup once in the playground, then run the transfer separately. These examples use persistent keys; backticks quote key names containing slashes.

SET `accounts/alice` 100
SET `accounts/bob` 50

Setup: a bare multi-statement script auto-commits.

BEGIN (locking=optimistic,
       decisionDurability=durable)
  LET src = GET `accounts/alice`
  LET dst = GET `accounts/bob`
  IF to_int(src) < 10 THEN
    THROW "Insufficient balance"
  END
  SET `accounts/alice` to_int(src) - 10
  SET `accounts/bob` to_int(dst) + 10
  COMMIT
END

Listing 1. After a successful commit, Alice has 90 and Bob has 60. Optimistic mode checks the read dependencies; explicit durable mode rejects ephemeral modifications.

If a competing transaction changes an observed balance, this attempt can abort. Start a new transaction and read again after a definite abort. A timeout or an uncertain commit is different: resolve that attempt before repeating the transfer.

The shared accounts/ bucket normally places these keys together. The same persistent protocol supports keys on different partitions, but locality alone does not guarantee the one-proposal optimization described in Section VI.

II. The Vocabulary

You can read the rest of the paper with these definitions:

  • Partition: a group of keys with its own replication and ordering. Its leader coordinates writes; replicas retain copies.
  • Raft and quorum: the replication protocol and the required majority of voters that agree on a partition's ordered records.
  • Coordinator: the server component tracking the live transaction. A participant is a partition doing work for it.
  • Revision: a key's version number. A write base is the committed version from which a change was computed.
  • MVCC: multi-version concurrency control. Proposed values remain separate from committed values, and retained older versions support historical reads.
  • Prepared intent: a replicated proposed change, including its value or deletion marker and transaction identity. It is recoverable work, not proof of commit.
  • Anchor: the partition holding the authoritative, or canonical, transaction decision. Its routing key comes from the first confirmed persistent mutation.
  • Lease and term: a lease limits how long a lock lives; a Raft term identifies a leadership epoch.
  • HLC: a Hybrid Logical Clock combines physical time with logical ordering. Transaction identity, commit time, and historical read time serve different purposes.
  • Materialization and settlement: install committed values in the normal key/value projection, then finish participant work and remove intents.

An actor is a local worker that processes one message at a time. Actors serialize local state changes; Raft orders replicated changes. An actor can handle keys from several partitions.

III. What Survives a Failure?

Persistent modifications use replicated prepared intents and a canonical decision under both BestEffort, the default decision policy, and Durable. Explicit durable mode enforces an all-persistent modified set. Ephemeral modifications are in-memory work; a mixed best-effort transaction is not crash-atomic across the two durability classes.

Persistent process-loss recovery also requires persistent write-ahead log (WAL) storage and durable write settings. Selecting persistent key operations does not make an in-memory embedded deployment survive process loss. See Durability Levels.

The live session and its unprepared staging remain in memory. Durable finalization preserves prepared work and the decision; it does not persist the entire interactive session from Begin. Read-only transactions have no modified persistent participant set and do not create a durable decision anchor.

Two ways to run the work

Scripts execute server-side, reducing client round trips. Bare multi-statement scripts auto-commit; explicit BEGIN … COMMIT END blocks control the transaction. Eligible single commands can take a direct path without the full coordinator.

Interactive transactions let application code send reads and writes between begin and commit. Both forms are available through REST, gRPC, and the embedded API. The server owns the working set; the client holds a transaction handle, not an authoritative list of writes.

Optional priority admission limits starts through separate script and session gates. It is disabled by default. Refusal means no transaction began, so the caller can back off and try again. Admission changes resource usage, not conflict rules.

IV. Reads, Writes, and Conflicts

An accepted transactional write stages a value and a write intent in the owning actor. The transaction can read its own staged writes; other transactions cannot treat them as committed data. Staging alone has not made the proposed value recoverable through Raft.

Pessimistic reads use exclusive point locks; prefix or range locks can protect scanned groups. Optimistic reads avoid read locks and enable read-set validation. Writes still establish exclusion and intent state. These key/value transaction locks are separate from Kahuna's distributed-lock API.

Latest reads are pinned per key

The first latest transactional point read records the committed value or absence for that key. A later point read or write can abort early if the committed revision moved past that observation. The transaction still sees its own staged value. Commit validates registered dependencies as well.

Reading Alice and then Bob for the first time can observe different moments. Per-key observations do not create a shared transaction-start snapshot. Optimistic scans track returned keys, not all the gaps where a new key could appear. Such an insertion is called a phantom; use appropriate prefix or range locking when the business rule depends on a whole group.

Historical reads are read-only

A fixed nonzero ReadTimestamp selects retained versions committed at or before that HLC. Historical transactions reject writes and cannot combine that timestamp with tracked latest-read validation. A snapshot hold protects retained history; it cannot restore pruned revisions or make an arbitrary future timestamp safe.

Historical reads can wait or return MustRetry while relevant writes, unflushed history, or clock checks prevent a safe answer. Expiration is evaluated at the current read time: a fixed timestamp does not freeze TTL. The lower-level StatementSnapshot read mode is a separate facility, described in Transaction Reads and Locks.

Failover can invalidate earlier work

Transaction locks and unprepared staging are leader-local. A leader change can remove them while the session remains on its original coordinator node. Acquiring a replacement lock does not make a computation based on earlier reads safe again.

Commit checks the original lock-grant terms, observed range-lock lapses, staged revision continuity, and ownership of the original staged intents. A successful staged-intent probe holds the intent through commit rather than merely renewing its ordinary lease. Interactive sessions with lost exclusion receive terminal Aborted; self-contained scripts map that refusal to MustRetry so they can rerun their computation.

These checks have boundaries: lock-lapse evidence is node-local and retained for a bounded period, older nodes may not report grant terms, and a range lease expiring between one-phase validation and apply is not covered by the observed-lapse check. Do not infer unconditional serializability from the presence of locks.

V. Prepare, Validate, Decide

Two-phase commit separates preserving the proposed changes from deciding their outcome. The normal persistent path is:

  1. Close and freeze. Stop new operations, drain already registered work, and freeze the confirmed working set. Commit, rollback, and abandoned-session cleanup share one finalization slot.
  2. Build the input. Record exact participant effects, their base revisions, the participant manifest, commit timestamp, routing generations, and decision deadline. The manifest identifies the complete persistent write set.
  3. Prepare. Replicate the proposed effects. Anchor-record initialization and the anchor prepare share an atomic proposal; other participant partitions prepare concurrently.
  4. Check dependencies. Prepared-base fences check whether read-modify-write changes still derive from acceptable committed versions. Commit probes check foreign writers, covering range locks, and exclusion continuity; read validation compares recorded existence and revision.
  5. Decide. A proven conflict prevents commit. The anchor record chooses one terminal outcome, commit or abort. Participants follow that canonical outcome even if a retry or recovery request proposed the opposite.
  6. Settle. Install committed effects or discard aborted work, release locks, and remove resolved intents. With deferred settlement, commit can return before this work finishes.

Replicated preparation and logical prepare success are distinct: a proposal can reach the log while a base fence refuses to acknowledge its proposed change. The two-phase path also collects participant-replica fence verdicts before deciding; a stale-base verdict forces abort. Missing verdicts do not block commit in this exchange, so it must not be described as unanimous replica approval.

Ordinary commit probes have a different contract: an inconclusive returned answer yields MustRetry, while a missing result for a requested key violates the probe contract and aborts. An infrastructure failure must not be presented as a proven data conflict.

Key distinction. Prepared means the proposed effect is recoverable. Committed means the canonical decision authorizes it. Materialized means the normal key/value projection has caught up.

VI. When One Raft Proposal Is Enough

An eligible transaction whose persistent writes and anchor share one partition can combine initialization, preparation, and decision in one atomic Raft proposal. A remote coordinator can forward that bundle to the anchor leader. One partition is necessary, but dependency checks and configuration also determine eligibility.

In a multi-process group, the default OnePhaseApplyTimeValidation = false excludes transactions with validated write bases, read dependencies beyond their writes, or recorded lock grants. They use the standard two-phase path.

With apply-time validation enabled, replicas check written bases and same-partition persistent point dependencies against the replicated committed-head ledger in log order. This permits more read-modify-write transactions to use one proposal. Validated predicate dependencies, off-partition reads, and non-persistent read dependencies still prevent that optimization in multi-process groups.

The bundle also fences the anchor leadership term before append. With apply-time validation, the replicated check enforces that term again. A single-process group relaxes some eligibility restrictions and accepts an in-process validation-to-apply window; that topology setting must not be used for a group that can acquire remote replicas.

Enable apply-time validation only after every node supports the persisted ledger and extended checks. StagedBaseFenceRetentionMs must match across nodes. Older snapshots without a ledger need the documented migration. See one-phase configuration and compatibility.

VII. Reading Before Settlement Finishes

Suppose Alice's old value is 100 and a prepared intent contains 90. A read that encounters that intent consults its canonical decision: commit makes 90 visible; abort leaves the earlier committed state; an unresolved decision requires waiting or retrying rather than guessing. Historical reads also respect the intent's commit timestamp and safe-time checks.

Scans merge committed intents too. A newer committed head can supersede a lingering intent; the old intent must not resurrect an overwritten or deleted key. Equal revisions need timestamp checks because EXTEND changes expiry without advancing the revision.

By default, DurableDeferredSettlement = true lets commit return before settlement. Separate materialization records install values before settlement removes their intents. DurableMaterializeByReference = true makes those records reference the already replicated intent instead of copying its value again.

The opt-in DurableMaterializeOnResolve path installs values while applying the settlement record, before removing the intents. It has replica compatibility requirements. Neither settlement mode means every backend row has already flushed when commit returns.

Recovery metadata and application-durability floors keep log compaction from discarding state still needed by asynchronous backend persistence. See Durable Transaction Settlement for encodings and upgrade requirements.

VIII. Recovery and Range Moves

An undecided transaction whose coordinator disappears can be aborted after its durable decision deadline. Recovery must establish that abort at the anchor; elapsed time alone is not a decision. A late coordinator cannot change an established abort into commit.

The deadline uses commit HLC plus an adaptive window derived from recent finalization latency and the number of prepared intents, so a large write set can receive a larger window. The default multiplier is four, with bounds of 5–60 seconds. This is a recovery window, separate from the session timeout. A live coordinator making progress can extend the deadline through a replicated transition while its lease remains valid; the default allows up to eight extensions per attempt. Set DurableDecisionDeadlineMaxExtensions = 0 during a mixed-version rollout with nodes that cannot decode renewals. Recovery still needs the required anchor quorum.

Participant leaders inspect prepared intents: committed decisions are materialized and settled; aborted decisions are cleared; undecided work remains pending before its deadline. After the permitted window, recovery can establish an abort, including an abort tombstone when the record is missing. A worker racing a valid commit must follow the actual canonical winner.

A range split or merge must not drop unresolved transaction state. The transfer path settles decided intents and refuses cutover while undecided intents remain or inspection cannot be trusted. It transfers required completion metadata, then changes routing generations. Queued writes check their generation again at dispatch; resolvers use current key placement.

IX. Retries Are Part of the Protocol

Each interactive operation carries an identity and request digest. Reusing the identity for the same request can join pending work or replay a completed response; reusing it for different work is rejected. Participant and session caches are bounded, in-memory retry aids, not permanent operation histories.

Table IIWhat the caller should do

OutcomeNext action
CommittedSuccess. Do not repeat the business changes.
AbortedTerminal. Retry the business operation in a new transaction with fresh reads.
RolledBackCleanup acknowledged; the attempt is finished.
MustRetryFor uncertain interactive finalization, retry the same handle. Do not add operations after closing.
ErroredUnknown, expired, or unavailable outcome; reconcile at the application boundary. This is not proof of rollback.
InvalidInputCorrect the request or option combination.
AdmissionRefusedNo transaction started. Back off before a new attempt.

The self-contained script lost-exclusion case in Section IV is a specific rerun path. A general timeout or MustRetry must not be interpreted as permission to duplicate an uncertain transfer. Durable transaction identity is also not a permanent business-level idempotency key.

X. Guarantees and Limits

Persistent participants share one recoverable decision once durable preparation and finalization are established, subject to the configured persistence and quorum assumptions. Ephemeral participants and pre-prepare session state have weaker failure behavior.

Isolation depends on read mode, tracked dependencies, locking, and failure handling. Optimistic scans do not protect gaps. Latest reads do not create a shared timestamp. Historical transactions are read-only. HLC ordering alone does not establish external consistency or a bounded-clock commit-wait guarantee.

This review checks implementation and repository documentation; it is neither a formal proof nor a fresh distributed fault campaign. The earlier paper's release-specific claim about an unfinished 1.5.3 soak is not evidence about today's code. Current safeguards include staging-continuity checks, lock-term checks, replica-fence confirmation, and optional apply-time validation. Their presence is not proof that every failure schedule is safe.

No throughput or latency claim is made here. Evaluate contention, participant counts, retry behavior, quorum loss, and recovery under the deployment configuration you intend to run.
