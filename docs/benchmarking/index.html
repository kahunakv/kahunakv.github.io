Benchmarking Kahuna

kahuna-bench tells you how much load a Kahuna installation sustains and how fast it answers. It drives traffic through the normal Kahuna.Client network path and reports throughput and latency percentiles as a client sees them.

Use it to size a cluster before rollout, check tail latency at a required request rate, or compare versions, storage backends, and hardware.

Current Numbers​

One Kahuna 1.17.0 node on an 8-core Apple M3 laptop with 8 GB of memory. The benchmark client ran on the same machine, over cleartext gRPC, with 128-byte values and 10,000 keys.

In memory (--storage memory, --durability ephemeral). This is the cache, counter, and short-lived coordination path:

Point reads (get)705,654 req/s283 µs1.3 ms
Script RETURN 1 (script)581,440 req/s344 µs2.0 ms
50% reads, 50% writes (mixed)524,028 req/s386 µs1.6 ms
Writes (set)454,264 req/s451 µs1.8 ms
Batched writes, 100 keys per request (set-many)629,000 keys/s7.3 ms50.5 ms

Durable (--storage rocksdb, --durability persistent). Every write is committed through Raft and synced to disk before the client gets its answer:

In the durable mixed run, reads kept a 0.66 ms p99 while writes ran beside them at a 18.1 ms p99.

How these were measured:

  • 256 closed-loop workers unless the row says otherwise, 5 s warmup, 20 s measured. set-many used 64 workers.
  • Each row is the better of two runs: a node with one partition and a node with several (eight in memory, four durable). The two differed by less than 10% on most rows; durable writes and transactions were faster on one partition.
  • txn used --key-prefix bench/, which keeps a transaction's keys on one partition. Transactions that spanned four partitions reached 3,598 txn/s. Under 0.4% of transactions failed in either run; they are not counted.
  • Failed requests: 2 in two million sequence allocations, and at most 2 per run in the in-memory rows. The other rows had none.

A reference point. Valkey 9.1.2 on the same machine, default settings, no persistence, valkey-benchmark -c 64 without pipelining: 238,930 GET req/s, 241,488 SET req/s, and 208,030 req/s for a Lua counter equivalent to the rate limiter. The comparison is not like for like: the Kahuna client sends requests that are already waiting as one gRPC message (see Request Frames), and Kahuna used all eight cores while Valkey ran its default single I/O thread.

Three nodes. A local three-node cluster on an earlier release answered 29,948 mixed req/s with persistent durability and 256 workers. With several endpoints, leader-aware routing matters: learned routing reached 116,808 read req/s against 72,188 with round-robin.

These are measurements of one laptop, not guarantees. A server with more cores, faster storage, and a separate load generator will give different numbers. Run the tool on your own hardware before you plan capacity.

Run It​

Use a dedicated test environment

The workloads create and update keys under bench:, acquire locks, and may create the persistent sequence bench:seq:0. Do not point the tool at a production cluster unless that traffic and data are acceptable.

Install the .NET global tool:

dotnet tool install --global Kahuna.Benchmark

Benchmark a cluster. Pass one reachable node or every endpoint:

kahuna-bench \
  -c "https://kahuna-1:8082,https://kahuna-2:8082,https://kahuna-3:8082" \
  --workload mixed \
  --duration 60 \
  --concurrency 128

Benchmark a local development node. --insecure skips TLS validation for a self-signed certificate; localhost endpoints skip it automatically:

kahuna-bench -c https://127.0.0.1:8082 --workload mixed --duration 30

If the server exposes a cleartext gRPC port with --grpc-cleartext-ports, use that endpoint:

kahuna-bench -c http://127.0.0.1:8083 --workload mixed --duration 30

A run has three phases:

  1. Seed: create the keys that get or mixed read (at most 100,000), or the shared sequence.
  2. Warmup: generate load for --warmup seconds and discard the samples.
  3. Measure: record operations for --duration seconds and print the report.

Reproduce the Numbers Above​

Start one node with memory storage or RocksDB, then run the workload you want:

# In memory
kahuna-bench -c http://127.0.0.1:8083 --workload get   --durability ephemeral --concurrency 256
kahuna-bench -c http://127.0.0.1:8083 --workload mixed --durability ephemeral --concurrency 256
kahuna-bench -c http://127.0.0.1:8083 --workload set-many --durability ephemeral \
  --batch-size 100 --key-prefix bench/ --concurrency 64
kahuna-bench -c http://127.0.0.1:8083 --workload rate-limit --durability ephemeral \
  --rate-limit-budget 1000000 --concurrency 256

# Durable
kahuna-bench -c http://127.0.0.1:8083 --workload mixed    --concurrency 256
kahuna-bench -c http://127.0.0.1:8083 --workload set      --concurrency 512
kahuna-bench -c http://127.0.0.1:8083 --workload txn      --key-prefix bench/ --concurrency 256
kahuna-bench -c http://127.0.0.1:8083 --workload sequence --concurrency 256

The node answered 48,692 requests per second with no errors. Reads stayed under half a millisecond at p99. Writes took about 11 ms because each one waits for a replicated, synced commit.

ColumnMeaning
CountSuccessful measured operations
req/sSuccessful operations divided by measured time
p50 to p99.9Latency percentiles of successful requests. p99 is the latency 99% of requests stay within
max, meanSlowest and average successful request
errorsErrors plus timeouts. JSON and CSV report them separately
missesReads that found no value, or lock attempts that found the lock busy

Judge latency by p99 and p99.9, not by the median or by max. A low p50 with a high p99 means occasional stalls; one large max is a single request.

Errors and misses do not count toward req/s. A get or mixed run with --key-space above 100,000 reports misses, because seeding stops at 100,000 keys.

Workloads​

WorkloadWhat one operation does
setWrite one key
getRead one key
mixedRead or write one key; --read-pct sets the share of reads
deleteDelete one key
set-many, delete-manyWrite or delete --batch-size keys in one request
txnOpen an interactive transaction, write --keys-per-txn keys, commit
txn-getOpen a session, read one key --keys-per-txn times, roll back
bankTransfer between two seeded accounts in a contended transaction
rate-limitRun a script that counts a subject's requests in a window and admits or refuses
lockAcquire and release one lock
sequenceAllocate the next value of the shared sequence bench:seq:0
scriptExecute the script file given with --script

Keys are bench:{n} over --key-space. A small key space raises contention; a large one spreads the load.

# Contended read-modify-write transfers with optimistic locking
kahuna-bench -c "$ENDPOINTS" --workload bank --txn-locking optimistic --duration 60

# Your own server-side script
kahuna-bench -c "$ENDPOINTS" --workload script --script ./transfer.4gl --duration 60

# 1 KiB values
kahuna-bench -c "$ENDPOINTS" --workload set --value-size 1024 --duration 60

txn-get reports each round trip in its own row: txnstart, txngetfirst (first read), txngetfresh (first read after a write), txngetnext (later reads), and txnrollback. Its total counts round trips, not transactions. For time spent on the server, see the point-read stage metrics.

Find the Limit, or Verify a Rate​

The tool has two load modes, and they answer different questions.

Closed loop (default). Each worker sends a request, waits for the answer, and sends the next. Use it to find maximum throughput: raise --concurrency across runs until req/s stops growing.

kahuna-bench -c "$ENDPOINTS" --workload mixed --concurrency 256 --duration 60

A closed loop understates tail latency at saturation, because a slow answer also delays the next request.

Open loop (--rate). Requests start at a fixed rate, and latency is measured from the intended start time. Use it to measure p99 latency at a target rate, such as 20,000 requests per second.

kahuna-bench -c "$ENDPOINTS" --workload mixed --rate 20000 --concurrency 128 --duration 60

If the achieved req/s stays below the target while p99 climbs, the installation cannot sustain that rate. Open-loop pacing spins one thread, so keep a CPU core free for the load generator.

Compare Two Runs​

Keep everything except the thing under test identical, fix the seed, and save machine-readable output:

kahuna-bench -c "$ENDPOINTS" \
  --workload mixed --read-pct 50 \
  --warmup 10 --duration 60 \
  --concurrency 128 --key-space 100000 --value-size 256 \
  --seed 42 \
  --format json --output build-a.json

jq '.aggregate.p99Ms' build-a.json

JSON holds the run parameters plus per-operation and aggregate statistics. Stable fields include rps, p50Ms, p99Ms, p999Ms, errors, timeouts, and misses. --format csv writes the same rows as CSV. Progress goes to stderr, so stdout stays clean for a pipe.

For results you intend to rely on:

  • Run the load generator on a separate machine, so it does not take CPU from Kahuna.
  • Warm up for at least 10 seconds and measure for at least 60.
  • Start each run from the same server data.

Request Frames​

When several key/value requests are already waiting on one stream, the .NET client sends them in one gRPC message and the server answers them together. This cuts transport overhead without holding a request back to fill a frame. Frames cover key/value requests, scripts, scans, and interactive transaction calls; lock and sequence requests go one per message.

Frames are on by default. Pass --no-request-frames to measure what they contribute:

kahuna-bench -c http://127.0.0.1:8083 --workload get --durability ephemeral --duration 10
kahuna-bench -c http://127.0.0.1:8083 --workload get --durability ephemeral --duration 10 --no-request-frames

Routing​

kahuna-bench uses the same leader-aware routing as Kahuna.Client, and the report header prints the mode in effect: Learned (auto) with several endpoints, RoundRobin (auto) with one.

Force a mode to measure the cost of forwarded requests:

kahuna-bench -c "$ENDPOINTS" --workload get --routing roundrobin --duration 60
kahuna-bench -c "$ENDPOINTS" --workload get --routing learned --routing-counters --duration 60

--routing-counters proves the mode is in use. Few cache hits in a learned run mean the working set is larger than RouteCacheCapacity. A rising hints_rejected[endpoint_rejected] means the servers advertise endpoints this process cannot dial; map them with --routing-endpoint-map.

What It Does Not Do​

kahuna-bench is a load generator. It does not check correctness and it does not profile the server. For correctness under faults, see the Kahuna Jepsen suite, which tests key/value registers, locks, transactions, the sequencer, and membership changes with fault injection.
